## はじめに

この記事では、Spring MVC Kotlinで開発していたAPIの負荷が高いエンドポイントを、WebFluxとCoroutinesを使って書き換えた経験を共有します。

### 想定読者

- Spring MVC Kotlinを使用している開発者
- WebFluxやリアクティブプログラミングの経験がない方
- APIのパフォーマンス改善に興味がある方

### この記事で得られること

- WebFluxへ移行する具体的な理由と判断基準
- FeignClientからWebClientへの移行方法
- Coroutinesを本来の並列処理として活用する方法
- 実装時の注意点とベストプラクティス

## 背景：なぜWebFluxへ移行したのか

### 抱えていた問題

私たちのチームでは、Spring MVC Kotlinでマイクロサービスアーキテクチャのシステムを運用していました。ある特定のAPIエンドポイントで、以下のような問題が発生していました。

- **スレッド数の増大**：I/O待ちの処理が発生するたびに新しいスレッドを起動
- **リソースの無駄遣い**：スレッドはメモリを消費するが、ほとんどの時間は待機状態
- **スケーラビリティの限界**：負荷が高まるとスレッド数が急増し、サーバーリソースを圧迫

### Coroutinesを使っていたのに…

実は、すでにコードはCoroutinesで書いていました。しかし、**その恩恵は「コードの見やすさ」だけ**でした。

```kotlin
// 従来の実装（Spring MVC + Coroutines）
@RestController
@RequestMapping("/api/users")
class UserController(
    private val userClient: UserFeignClient,
    private val orderClient: OrderFeignClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        // 見た目は並列処理風だが、実際にはスレッドベースの処理
        val userDeferred = async { userClient.getUser(id) }
        val ordersDeferred = async { orderClient.getOrders(id) }
        
        val user = userDeferred.await()
        val orders = ordersDeferred.await()
        
        UserDetailsResponse(user, orders)
    }
}
```

このコードの問題点：

1. **FeignClientはブロッキングI/O**：内部的にはスレッドをブロックして通信
2. **async/awaitは新しいスレッドを起動**：並列処理のために別スレッドを生成
3. **Coroutinesの真の力を発揮できていない**：ノンブロッキングではない

つまり、**「見やすく書けるだけのマルチスレッド処理」**になっていました。

## 解決策：WebFlux + Coroutinesへの移行

### なぜWebFluxを選んだのか

WebFluxへの移行を決めた理由は以下の通りです。

1. **既にCoroutinesで書いていた**：コードの大幅な書き換えが不要
2. **ノンブロッキングI/Oの実現**：スレッドをブロックせずに並列処理が可能
3. **リソース効率の向上**：少ないスレッド数で多数のリクエストを処理可能

### 重要な認識：WebFluxはリアクティブストリーミングのためだけではない

多くの記事では、WebFluxを「リアクティブストリーミング」や「バックプレッシャー」と結びつけて説明しています。しかし、**私たちの目的は違いました**。

**私たちの目的**：

- ✅ Coroutinesを真の並列処理として活用する
- ✅ ノンブロッキングI/Oでリソースを効率化する
- ✅ 負荷の高いエンドポイントのスケーラビリティを向上させる

**目的ではないこと**：

- ❌ リアクティブストリーミングの実装
- ❌ Flux/Monoベースの完全なリアクティブアーキテクチャ
- ❌ システム全体のリアクティブ化

WebFluxはリアクティブストリーミングのためだけのフレームワークではなく、**ノンブロッキングI/Oを実現するための基盤**として優れています。

## 実装方針

### 1. FeignClient → WebClient への移行

FeignClientはブロッキングI/Oなので、ノンブロッキングなWebClientに置き換えます。

#### Before: FeignClient

```kotlin
@FeignClient(name = "user-service", url = "\${services.user.url}")
interface UserFeignClient {
    @GetMapping("/users/{id}")
    fun getUser(@PathVariable id: String): UserResponse
}
```

#### After: WebClient

```kotlin
@Component
class UserWebClient(
    private val webClientBuilder: WebClient.Builder,
    @Value("\${services.user.url}") private val baseUrl: String
) {
    private val webClient: WebClient = webClientBuilder
        .baseUrl(baseUrl)
        .build()
    
    suspend fun getUser(id: String): UserResponse {
        return webClient
            .get()
            .uri("/users/{id}", id)
            .retrieve()
            .awaitBody()
    }
}
```

ポイント：

- `awaitBody()`を使うことで、Coroutinesと統合
- 内部的にはノンブロッキングI/Oで通信
- 戻り値は`suspend fun`で定義し、Coroutinesの恩恵を受ける

### 2. Controllerの実装

```kotlin
@RestController
@RequestMapping("/api/users")
class UserController(
    private val userWebClient: UserWebClient,
    private val orderWebClient: OrderWebClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        // 真の並列処理を実現
        val userDeferred = async { userWebClient.getUser(id) }
        val ordersDeferred = async { orderWebClient.getOrders(id) }
        
        val user = userDeferred.await()
        val orders = ordersDeferred.await()
        
        UserDetailsResponse(user, orders)
    }
}
```

見た目は変わりませんが、**中身は全く違います**。

#### 従来（Spring MVC）の動作

1. `async`ブロックごとに新しいスレッドを起動
2. FeignClientがHTTP通信中、スレッドはブロック（待機）
3. 待機中のスレッドはメモリを消費するが何もしない
4. 通信完了後、結果を受け取ってスレッドを破棄

#### WebFluxでの動作

1. `async`ブロックはCoroutineコンテキスト内で起動
2. WebClientがHTTP通信を開始し、すぐに制御を返す（ノンブロッキング）
3. スレッドは他の処理を実行できる（別のリクエストなど）
4. 通信完了のコールバックを受けて、Coroutineが再開

**結果**：同じスレッド数で、より多くのリクエストを並列処理できる

### 3. WebClient の設定

WebClientの設定をカスタマイズして、タイムアウトやコネクションプールを適切に設定します。

```kotlin
@Configuration
class WebClientConfig {
    
    @Bean
    fun webClientBuilder(): WebClient.Builder {
        val httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 5000)
            .responseTimeout(Duration.ofSeconds(5))
            .doOnConnected { conn ->
                conn.addHandlerLast(ReadTimeoutHandler(5000, TimeUnit.MILLISECONDS))
                    .addHandlerLast(WriteTimeoutHandler(5000, TimeUnit.MILLISECONDS))
            }
        
        return WebClient.builder()
            .clientConnector(ReactorClientHttpConnector(httpClient))
    }
}
```

## 実装時の注意点

### 1. すべてをWebFluxにする必要はない

**段階的な移行**が可能です。私たちは以下のアプローチを取りました。

- ✅ 負荷の高い特定のエンドポイントのみWebFlux化
- ✅ 他のエンドポイントは従来のSpring MVCのまま
- ✅ 同じアプリケーション内で両方を共存させる

Spring Bootでは、WebFluxとSpring MVCを同時に使うことはできませんが、**マイクロサービスアーキテクチャなら、サービスごとに選択できます**。

### 2. データベースアクセスも考慮する

WebClientをノンブロッキングにしても、データベースアクセスがブロッキングなら意味が薄れます。

#### 選択肢

1. **R2DBC**（Reactive Relational Database Connectivity）
   - リレーショナルDBのリアクティブドライバ
   - 学習コストは高いが、完全にノンブロッキング

2. **Coroutinesとの組み合わせ**
   - Exposedなどのライブラリを使う
   - ある程度の学習コストで導入可能

3. **読み取り専用なら、ブロッキングでも許容**
   - 書き込みが少ない場合は、従来のJPAのままでも効果はある

私たちのケースでは、対象エンドポイントはDB読み取りが少なく、主に外部API呼び出しが多かったため、**WebClientの移行だけで十分な効果**が得られました。

### 3. エラーハンドリング

WebClientのエラーハンドリングは、FeignClientと異なります。

```kotlin
suspend fun getUser(id: String): UserResponse {
    return try {
        webClient
            .get()
            .uri("/users/{id}", id)
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError) { response ->
                Mono.error(ClientException("Client error: ${response.statusCode()}"))
            }
            .onStatus(HttpStatusCode::is5xxServerError) { response ->
                Mono.error(ServerException("Server error: ${response.statusCode()}"))
            }
            .awaitBody()
    } catch (e: WebClientResponseException) {
        // WebClientの例外をビジネス例外に変換
        throw UserNotFoundException("User not found: $id", e)
    }
}
```

### 4. テストの変更

WebClientを使用する場合、テストも変更が必要です。

#### MockWebServerを使用したテスト

```kotlin
@SpringBootTest
class UserWebClientTest {
    
    private lateinit var mockWebServer: MockWebServer
    private lateinit var userWebClient: UserWebClient
    
    @BeforeEach
    fun setUp() {
        mockWebServer = MockWebServer()
        mockWebServer.start()
        
        val webClientBuilder = WebClient.builder()
        userWebClient = UserWebClient(
            webClientBuilder,
            mockWebServer.url("/").toString()
        )
    }
    
    @AfterEach
    fun tearDown() {
        mockWebServer.shutdown()
    }
    
    @Test
    fun `getUser should return user when API returns 200`() = runBlocking {
        // Given
        val mockResponse = MockResponse()
            .setBody("""{"id": "123", "name": "Test User"}""")
            .setResponseCode(200)
            .addHeader("Content-Type", "application/json")
        mockWebServer.enqueue(mockResponse)
        
        // When
        val result = userWebClient.getUser("123")
        
        // Then
        assertEquals("123", result.id)
        assertEquals("Test User", result.name)
    }
}
```

## 効果測定

WebFluxへの移行後、以下の効果が得られました。

### パフォーマンス指標

| 指標 | 移行前 | 移行後 | 改善率 |
|------|--------|--------|--------|
| レスポンスタイム（平均） | 850ms | 320ms | **62%改善** |
| スループット（req/s） | 120 | 380 | **217%向上** |
| CPU使用率（ピーク時） | 85% | 45% | **47%削減** |
| メモリ使用率（ピーク時） | 78% | 52% | **33%削減** |

### リソース効率

- **スレッド数**：200 → 50（75%削減）
- **コンテキストスイッチ**：大幅減少
- **GC頻度**：減少（メモリ圧迫が軽減）

これらの改善により、**同じインフラコストでより多くのリクエストを処理**できるようになりました。

## まとめ

Spring MVC KotlinからWebFlux + Coroutinesへの移行により、以下を実現できました。

✅ **Coroutinesを真の並列処理として活用**：ノンブロッキングI/Oとの組み合わせで本来の力を発揮

✅ **リソース効率の大幅改善**：スレッド数を75%削減しながら、スループットは217%向上

✅ **段階的な移行が可能**：負荷の高いエンドポイントから順次適用

✅ **既存のコードとの互換性**：Coroutinesベースのコードはほぼそのまま流用可能

### WebFlux移行を検討すべきケース

- 外部API呼び出しが多いエンドポイント
- I/O待ちが多く、スレッドの待機時間が長い
- 既にCoroutinesでコードを書いている

### 移行しなくてもよいケース

- CPU集約的な処理が中心
- リクエスト数が少ない
- レガシーコードが多く、リスクが高い
