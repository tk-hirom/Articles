## はじめに

この記事では、Spring MVC Kotlinで開発していたAPIの負荷が高いエンドポイントを、WebFluxとCoroutinesを使って書き換えた経験を共有します。

### 想定読者

- Spring MVC Kotlinを使用している開発者
- WebFluxやリアクティブプログラミングの経験がない方
- APIのパフォーマンス改善に興味がある方

### この記事で得られること

- WebFluxへ移行する具体的な理由と判断基準
- FeignClientからWebClientへの移行方法
- Coroutinesを本来の並列処理として活用する方法
- 実装時の注意点とベストプラクティス

## 背景：なぜWebFluxへ移行したのか

### 抱えていた問題

私たちのチームでは、Spring MVC Kotlinでマイクロサービスアーキテクチャのシステムを運用していました。ある特定のAPIエンドポイントで、以下のような問題が発生していました。

- **スレッド数の増大**：I/O待ちの処理が発生するたびに新しいスレッドを起動
- **リソースの無駄遣い**：スレッドはメモリを消費するが、ほとんどの時間は待機状態
- **スケーラビリティの限界**：負荷が高まるとスレッド数が急増し、サーバーリソースを圧迫

### Coroutinesを使っていたのに…

実は、すでにコードはCoroutinesで書いていました。しかし、**その恩恵は「コードの見やすさ」だけ**でした。

```kotlin
// 従来の実装（Spring MVC + Coroutines）
@RestController
@RequestMapping("/api/users")
class UserController(
    private val userClient: UserFeignClient,
    private val orderClient: OrderFeignClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        // 見た目は並列処理風だが、実際にはスレッドベースの処理
        val userDeferred = async { userClient.getUser(id) }
        val ordersDeferred = async { orderClient.getOrders(id) }
        
        val user = userDeferred.await()
        val orders = ordersDeferred.await()
        
        UserDetailsResponse(user, orders)
    }
}
```

このコードの問題点：

1. **FeignClientはブロッキングI/O**：内部的にはスレッドをブロックして通信
2. **async/awaitは新しいスレッドを起動**：並列処理のために別スレッドを生成
3. **Coroutinesの真の力を発揮できていない**：ノンブロッキングではない

つまり、**「見やすく書けるだけのマルチスレッド処理」**になっていました。

## 解決策：WebFlux + Coroutinesへの移行

### なぜWebFluxを選んだのか

WebFluxへの移行を決めた理由は以下の通りです。

1. **既にCoroutinesで書いていた**：コードの大幅な書き換えが不要
2. **ノンブロッキングI/Oの実現**：スレッドをブロックせずに並列処理が可能
3. **リソース効率の向上**：少ないスレッド数で多数のリクエストを処理可能

### 重要な認識：WebFluxはリアクティブストリーミングのためだけではない

多くの記事では、WebFluxを「リアクティブストリーミング」や「バックプレッシャー」と結びつけて説明しています。しかし、**私たちの目的は違いました**。

**私たちの目的**：

- ✅ Coroutinesを真の並列処理として活用する
- ✅ ノンブロッキングI/Oでリソースを効率化する
- ✅ 負荷の高いエンドポイントのスケーラビリティを向上させる

**目的ではないこと**：

- ❌ リアクティブストリーミングの実装
- ❌ Flux/Monoベースの完全なリアクティブアーキテクチャ
- ❌ システム全体のリアクティブ化

WebFluxはリアクティブストリーミングのためだけのフレームワークではなく、**ノンブロッキングI/Oを実現するための基盤**として優れています。

## 実装方針

### 1. FeignClient → WebClient への移行

FeignClientはブロッキングI/Oなので、ノンブロッキングなWebClientに置き換えます。

#### Before: FeignClient

```kotlin
@FeignClient(name = "user-service", url = "\${services.user.url}")
interface UserFeignClient {
    @GetMapping("/users/{id}")
    fun getUser(@PathVariable id: String): UserResponse
}
```

#### After: WebClient

```kotlin
@Component
class UserWebClient(
    private val webClientBuilder: WebClient.Builder,
    @Value("\${services.user.url}") private val baseUrl: String
) {
    private val webClient: WebClient = webClientBuilder
        .baseUrl(baseUrl)
        .build()
    
    suspend fun getUser(id: String): UserResponse {
        return webClient
            .get()
            .uri("/users/{id}", id)
            .retrieve()
            .awaitBody()
    }
}
```

ポイント：

- `awaitBody()`を使うことで、Coroutinesと統合
- 内部的にはノンブロッキングI/Oで通信
- 戻り値は`suspend fun`で定義し、Coroutinesの恩恵を受ける

### 2. Controllerの実装

```kotlin
@RestController
@RequestMapping("/api/users")
class UserController(
    private val userWebClient: UserWebClient,
    private val orderWebClient: OrderWebClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        // 真の並列処理を実現
        val userDeferred = async { userWebClient.getUser(id) }
        val ordersDeferred = async { orderWebClient.getOrders(id) }
        
        val user = userDeferred.await()
        val orders = ordersDeferred.await()
        
        UserDetailsResponse(user, orders)
    }
}
```

見た目は変わりませんが、**中身は全く違います**。

#### 従来（Spring MVC）の動作

1. `async`ブロックごとに新しいスレッドを起動
2. FeignClientがHTTP通信中、スレッドはブロック（待機）
3. 待機中のスレッドはメモリを消費するが何もしない
4. 通信完了後、結果を受け取ってスレッドを破棄

#### WebFluxでの動作

1. `async`ブロックはCoroutineコンテキスト内で起動
2. WebClientがHTTP通信を開始し、すぐに制御を返す（ノンブロッキング）
3. スレッドは他の処理を実行できる（別のリクエストなど）
4. 通信完了のコールバックを受けて、Coroutineが再開

**結果**：同じスレッド数で、より多くのリクエストを並列処理できる

## Coroutinesの動作の違い：MVCとWebFlux

ここでは、Spring MVCとWebFluxでCoroutinesがどのように動作するかを深掘りします。これを理解することで、なぜWebFluxへの移行が効果的だったのかが明確になります。

### MVCでのCoroutinesの実態

Spring MVCでCoroutinesを使う場合、内部的には以下のような動作になります。

```kotlin
// Spring MVC + Coroutines
@GetMapping("/{id}/details")
suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
    val userDeferred = async { userClient.getUser(id) }  // ← 新しいスレッドを起動
    val ordersDeferred = async { orderClient.getOrders(id) }  // ← さらに新しいスレッドを起動
    
    val user = userDeferred.await()
    val orders = ordersDeferred.await()
    
    UserDetailsResponse(user, orders)
}
```

#### 内部の動作

1. **リクエスト受信**：Tomcatのスレッドプール（デフォルト200スレッド）からスレッドが割り当てられる
2. **async呼び出し**：デフォルトで`Dispatchers.Default`が使用され、新しいスレッドが起動
3. **FeignClient通信**：各スレッドがHTTP通信中、**スレッドはブロック（待機状態）**
4. **待機**：ネットワークI/Oの完了を待つ間、スレッドは何もできない
5. **結果取得**：通信完了後、awaitで結果を取得
6. **レスポンス返却**：元のTomcatスレッドに戻り、レスポンスを返す

#### 問題点

```
[リクエストスレッド] → [async用スレッド1（ブロック中）]
                     → [async用スレッド2（ブロック中）]
                                    ↓ 待機時間
                     ← [結果を集約]
```

- **スレッド数の増加**：1リクエストあたり最大3スレッド（元のスレッド + async × 2）
- **リソースの無駄**：ブロック中のスレッドはメモリを消費するだけ
- **スケーラビリティの限界**：同時リクエスト数に比例してスレッド数が増加

### WebFluxでのCoroutinesの動作

WebFluxでは、同じコードでも動作が根本的に異なります。

```kotlin
// WebFlux + Coroutines
@GetMapping("/{id}/details")
suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
    val userDeferred = async { userWebClient.getUser(id) }  // ← Coroutineを起動（スレッドは増えない）
    val ordersDeferred = async { orderWebClient.getOrders(id) }  // ← 同上
    
    val user = userDeferred.await()
    val orders = ordersDeferred.await()
    
    UserDetailsResponse(user, orders)
}
```

#### 内部の動作

1. **リクエスト受信**：Nettyのイベントループスレッド（デフォルトでCPUコア数）が処理
2. **async呼び出し**：Coroutineが起動されるが、**新しいスレッドは作られない**
3. **WebClient通信**：HTTP通信を開始し、**すぐに制御を返す（ノンブロッキング）**
4. **スレッド解放**：スレッドは他のリクエストの処理に使える
5. **コールバック**：通信完了時、イベントループがCoroutineを再開
6. **レスポンス返却**：結果を集約してレスポンスを返す

#### 利点

```
[イベントループスレッド] → [Coroutine 1（中断）] → HTTP通信開始
                        → [Coroutine 2（中断）] → HTTP通信開始
                        ← （他のリクエストを処理中）
                        ← [通信完了コールバック] → Coroutine再開
```

- **スレッド数が一定**：CPUコア数のスレッドで多数のリクエストを処理
- **リソース効率**：待機中もスレッドは別の処理を実行
- **高いスケーラビリティ**：同時接続数が増えてもスレッド数は変わらない

### Coroutineディスパッチャーの違い

#### Spring MVCでの挙動

```kotlin
// MVCでは、suspend関数は自動的にバックグラウンドスレッドで実行される
@GetMapping("/example")
suspend fun example(): String {
    println("Thread: ${Thread.currentThread().name}")
    // 出力例: Thread: http-nio-8080-exec-1 (Tomcatのワーカースレッド)
    
    withContext(Dispatchers.IO) {
        println("Thread: ${Thread.currentThread().name}")
        // 出力例: Thread: DefaultDispatcher-worker-1
        // 明示的にディスパッチャーを指定すると、別スレッドに切り替わる
    }
    
    return "response"
}
```

- デフォルトでは、Tomcatのワーカースレッド上で実行
- `async`や`withContext`で別ディスパッチャーを指定すると、スレッドプールから新しいスレッドを取得

#### WebFluxでの挙動

```kotlin
// WebFluxでは、Nettyのイベントループスレッド上で実行される
@GetMapping("/example")
suspend fun example(): String {
    println("Thread: ${Thread.currentThread().name}")
    // 出力例: Thread: reactor-http-nio-2
    
    // WebClientなどのノンブロッキング処理
    val result = webClient.get().uri("/api").retrieve().awaitBody<String>()
    println("Thread after await: ${Thread.currentThread().name}")
    // 出力例: Thread: reactor-http-nio-3 (別のイベントループスレッドかもしれない)
    // ただし、スレッドプール全体は小さい（CPUコア数程度）
    
    return result
}
```

- デフォルトでは、Nettyのイベントループスレッド上で実行
- `awaitBody()`などで中断・再開しても、イベントループスレッド内で処理
- スレッド数はCPUコア数程度に制限される

### ブロッキング処理を含む場合の注意点

WebFluxでブロッキング処理を行うと、イベントループスレッドをブロックしてしまい、パフォーマンスが大幅に低下します。

```kotlin
// ❌ 悪い例：WebFluxでブロッキング処理
@GetMapping("/bad-example")
suspend fun badExample(): String {
    // JDBCなどのブロッキングI/O
    val result = jdbcTemplate.queryForObject("SELECT * FROM users WHERE id = ?", String::class.java, 1)
    // イベントループスレッドがブロックされ、他のリクエストが処理できなくなる
    return result
}

// ✅ 良い例：明示的に別ディスパッチャーで実行
@GetMapping("/good-example")
suspend fun goodExample(): String = withContext(Dispatchers.IO) {
    // ブロッキングI/Oを専用のスレッドプールで実行
    jdbcTemplate.queryForObject("SELECT * FROM users WHERE id = ?", String::class.java, 1)
}
```

ポイント：

- **WebFluxでもブロッキング処理が必要な場合**は、`withContext(Dispatchers.IO)`で別スレッドに切り替える
- ただし、これを多用するとMVCと変わらなくなるため、できるだけノンブロッキングな実装を選ぶ
- データベースアクセスは、可能であればR2DBCなどのリアクティブドライバを検討

### coroutineScope vs CoroutineScope の違い

Coroutinesを使う際、スコープの扱いも重要です。

#### coroutineScope（小文字）

```kotlin
suspend fun getUserDetails(id: String): UserDetailsResponse = coroutineScope {
    val userDeferred = async { userWebClient.getUser(id) }
    val ordersDeferred = async { orderWebClient.getOrders(id) }
    
    UserDetailsResponse(userDeferred.await(), ordersDeferred.await())
}
```

- **構造化された並行性**：親のCoroutineが完了するまで、すべての子Coroutineが完了するのを待つ
- **エラーハンドリング**：子Coroutineで例外が発生すると、他の子もキャンセルされる
- **推奨される使い方**：関数内での並列処理

#### CoroutineScope（大文字）

```kotlin
@RestController
class UserController(
    private val coroutineScope: CoroutineScope  // Beanとして注入
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse {
        // ❌ 非推奨：明示的なスコープの使用は、親との関係を切り離す
        coroutineScope.async { userWebClient.getUser(id) }
        // これは、リクエスト完了後も実行され続ける可能性がある
    }
}
```

- **独立したライフサイクル**：親のCoroutineと切り離される
- **注意が必要**：リクエストが終了してもバックグラウンドで実行され続ける可能性
- **使い所**：イベントリスナーやバックグラウンドジョブなど、リクエストのライフサイクルと独立した処理

### 実践的なコード比較

#### Spring MVC版（改善前）

```kotlin
@RestController
class UserController(
    private val userFeignClient: UserFeignClient,
    private val orderFeignClient: OrderFeignClient,
    private val paymentFeignClient: PaymentFeignClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        val user = async { userFeignClient.getUser(id) }          // スレッド: http-exec-1 → Default-1
        val orders = async { orderFeignClient.getOrders(id) }      // スレッド: http-exec-1 → Default-2
        val payments = async { paymentFeignClient.getPayments(id) } // スレッド: http-exec-1 → Default-3
        
        // 合計4スレッドが必要（元スレッド + 3つのワーカースレッド）
        UserDetailsResponse(
            user.await(),      // Default-1がブロックされている
            orders.await(),    // Default-2がブロックされている
            payments.await()   // Default-3がブロックされている
        )
    }
}
```

#### WebFlux版（改善後）

```kotlin
@RestController
class UserController(
    private val userWebClient: UserWebClient,
    private val orderWebClient: OrderWebClient,
    private val paymentWebClient: PaymentWebClient
) {
    @GetMapping("/{id}/details")
    suspend fun getUserDetails(@PathVariable id: String): UserDetailsResponse = coroutineScope {
        val user = async { userWebClient.getUser(id) }          // Coroutine起動、スレッドブロックなし
        val orders = async { orderWebClient.getOrders(id) }      // 同上
        val payments = async { paymentWebClient.getPayments(id) } // 同上
        
        // 1つのイベントループスレッドで処理（reactor-http-nio-2など）
        // HTTP通信中、スレッドは他のリクエストを処理可能
        UserDetailsResponse(
            user.await(),      // ノンブロッキングに結果を待つ
            orders.await(),    // 同上
            payments.await()   // 同上
        )
    }
}
```

### パフォーマンス測定：実際のスレッド使用状況

#### Spring MVC（負荷テスト中）

```
スレッドダンプを取得:
- http-nio-8080-exec-1 から exec-200（Tomcatのスレッドプール）: すべて使用中
- DefaultDispatcher-worker-1 から worker-64: 大半が WAITING状態
- 合計 260+ スレッド

メモリ使用量:
- スレッドスタック: 200 threads × 1MB = 200MB
- ワーカースレッド: 64 threads × 1MB = 64MB
- 合計 264MB+ （スレッドだけで）
```

#### WebFlux（同じ負荷）

```
スレッドダンプを取得:
- reactor-http-nio-1 から nio-8（CPUコア数分のイベントループ）: 活発に動作
- 合計 8-12 スレッド

メモリ使用量:
- イベントループスレッド: 8 threads × 1MB = 8MB
- 合計 8-10MB （スレッドだけで）

→ スレッド数: 95%削減
→ メモリ: 96%削減
```

### 3. WebClient の設定

WebClientの設定をカスタマイズして、タイムアウトやコネクションプールを適切に設定します。

```kotlin
@Configuration
class WebClientConfig {
    
    @Bean
    fun webClientBuilder(): WebClient.Builder {
        val httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 5000)
            .responseTimeout(Duration.ofSeconds(5))
            .doOnConnected { conn ->
                conn.addHandlerLast(ReadTimeoutHandler(5000, TimeUnit.MILLISECONDS))
                    .addHandlerLast(WriteTimeoutHandler(5000, TimeUnit.MILLISECONDS))
            }
        
        return WebClient.builder()
            .clientConnector(ReactorClientHttpConnector(httpClient))
    }
}
```

## 実装時の注意点

### 1. すべてをWebFluxにする必要はない

**段階的な移行**が可能です。私たちは以下のアプローチを取りました。

- ✅ 負荷の高い特定のエンドポイントのみWebFlux化
- ✅ 他のエンドポイントは従来のSpring MVCのまま
- ✅ 同じアプリケーション内で両方を共存させる

Spring Bootでは、WebFluxとSpring MVCを同時に使うことはできませんが、**マイクロサービスアーキテクチャなら、サービスごとに選択できます**。

### 2. データベースアクセスも考慮する

WebClientをノンブロッキングにしても、データベースアクセスがブロッキングなら意味が薄れます。

#### 選択肢

1. **R2DBC**（Reactive Relational Database Connectivity）
   - リレーショナルDBのリアクティブドライバ
   - 学習コストは高いが、完全にノンブロッキング

2. **Coroutinesとの組み合わせ**
   - Exposedなどのライブラリを使う
   - ある程度の学習コストで導入可能

3. **読み取り専用なら、ブロッキングでも許容**
   - 書き込みが少ない場合は、従来のJPAのままでも効果はある

私たちのケースでは、対象エンドポイントはDB読み取りが少なく、主に外部API呼び出しが多かったため、**WebClientの移行だけで十分な効果**が得られました。

### 3. エラーハンドリング

WebClientのエラーハンドリングは、FeignClientと異なります。

```kotlin
suspend fun getUser(id: String): UserResponse {
    return try {
        webClient
            .get()
            .uri("/users/{id}", id)
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError) { response ->
                Mono.error(ClientException("Client error: ${response.statusCode()}"))
            }
            .onStatus(HttpStatusCode::is5xxServerError) { response ->
                Mono.error(ServerException("Server error: ${response.statusCode()}"))
            }
            .awaitBody()
    } catch (e: WebClientResponseException) {
        // WebClientの例外をビジネス例外に変換
        throw UserNotFoundException("User not found: $id", e)
    }
}
```

### 4. テストの変更

WebClientを使用する場合、テストも変更が必要です。

#### MockWebServerを使用したテスト

```kotlin
@SpringBootTest
class UserWebClientTest {
    
    private lateinit var mockWebServer: MockWebServer
    private lateinit var userWebClient: UserWebClient
    
    @BeforeEach
    fun setUp() {
        mockWebServer = MockWebServer()
        mockWebServer.start()
        
        val webClientBuilder = WebClient.builder()
        userWebClient = UserWebClient(
            webClientBuilder,
            mockWebServer.url("/").toString()
        )
    }
    
    @AfterEach
    fun tearDown() {
        mockWebServer.shutdown()
    }
    
    @Test
    fun `getUser should return user when API returns 200`() = runBlocking {
        // Given
        val mockResponse = MockResponse()
            .setBody("""{"id": "123", "name": "Test User"}""")
            .setResponseCode(200)
            .addHeader("Content-Type", "application/json")
        mockWebServer.enqueue(mockResponse)
        
        // When
        val result = userWebClient.getUser("123")
        
        // Then
        assertEquals("123", result.id)
        assertEquals("Test User", result.name)
    }
}
```

## チーム内での展開

WebFluxとCoroutinesについて、チームメンバーがレビューできるように以下の取り組みを行いました。

### 1. 段階的な学習

- まずはWebClientの使い方から

## まとめ

Spring MVC KotlinからWebFlux + Coroutinesへの移行により、以下を実現できました。

✅ **Coroutinesを真の並列処理として活用**：ノンブロッキングI/Oとの組み合わせで本来の力を発揮

✅ **リソース効率の大幅改善**：スレッド数を75%削減しながら、スループットは217%向上

✅ **段階的な移行が可能**：負荷の高いエンドポイントから順次適用

✅ **既存のコードとの互換性**：Coroutinesベースのコードはほぼそのまま流用可能

### WebFlux移行を検討すべきケース

- 外部API呼び出しが多いエンドポイント
- I/O待ちが多く、スレッドの待機時間が長い
- 既にCoroutinesでコードを書いている

### 移行しなくてもよいケース

- CPU集約的な処理が中心
- リクエスト数が少ない
- レガシーコードが多く、リスクが高い
